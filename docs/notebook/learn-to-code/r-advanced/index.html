Goal

In Module 1 you learned to load, inspect, subset, and summarize the red spruce fitness-trait dataset with base R, and you wrote your first reproducible script. Module 2 does the same kinds of jobs with the tidyverse: a set of packages built for data wrangling (dplyr, tidyr), plotting (ggplot2), and repeating tasks (purrr). You will also fit your first statistical models.

By the end you will have a second script, src/02_wrangle_model_traits.R, that turns data/raw/ into a set of tables, publication-style figures, and model summaries in results/, all with one Rscript call.

Prerequisites

  • Completed Module 1 (you can read the file, use str(), table(), aggregate(), and save to results/)
  • R (>= 4.2), because the native pipe |> and the \(x) shorthand for functions need R 4.1 or newer
  • The dataset at data/raw/red_spruce_fitness_traits.txt, and the same cluster-exercise/ project layout as Module 1

TipCode reproducibility check

Installing is a one-time step, so it never goes inside your analysis script. The script only loads packages with library(). If a collaborator does not have a package, library() fails right away with a clear error. That is much better than the script quietly installing something into their system.

At the end of every script, sessionInfo() prints your R version and the version of every loaded package. Save that output with your results and anyone can see exactly which software produced them. Have you ever had code that worked last year and breaks today? Package versions are usually why.

NoteLogic check: “The following objects are masked from …”

When you run library(dplyr) in a fresh session, R prints something like:

The following objects are masked from 'package:stats':
    filter, lag

Two packages both define a function called filter(): base R’s stats (a signal-processing filter) and dplyr (keep rows). The package loaded last wins, so after library(dplyr) the bare name filter means dplyr::filter.

This is the second reason for the package::function syntax from Module 1. dplyr::filter(...) and stats::filter(...) are never ambiguous, whatever order the packages were loaded in. A classic bug is code that works in your session, then breaks for a collaborator who loaded the packages in a different order. If a familiar function suddenly gives a strange error, check conflicts() or write the package name explicitly.

I load broom and here with :: instead of library() because each is used only a few times. That keeps the list of loaded names short.

Making Region a meaningful factor

The three region codes describe where each population sits in the red spruce range: Core (the northern center of the range), Margin (Pennsylvania), and Edge (the southern Appalachians). R sorts factor levels alphabetically (C, E, M), which mixes up that geography. Mean latitude runs C 43.7°, M 41.2°, E 37.6°, so the order north to south is C → M → E. Let’s use that order:

traits <- traits |>
  mutate(Region = fct_relevel(factor(Region), "C", "M", "E"))

levels(traits$Region)
[1] "C" "M" "E"

From now on every table, boxplot, and model lists regions north to south. You choose this order once, near the top of the script, and it is used everywhere after that.

NoteLogic check: what does .groups = "drop" do?

When you summarise() a grouped tibble, dplyr removes the last grouping level but keeps any others. With a single group that leaves nothing grouped, but with group_by(Region, Population) the result is still grouped by Region. Any later mutate() or summarise() would then run separately inside each region, which can cause very confusing bugs.

.groups = "drop" removes all grouping, so the result is an ordinary tibble. Make it a habit. You can also use the per-call shortcut summarise(..., .by = Region), which groups for that one call only:

traits |> summarise(mean_height = mean(Height, na.rm = TRUE), .by = Region)
# A tibble: 3 × 2
  Region mean_height
  <fct>        <dbl>
1 E             28.9
2 C             29.7
3 M             34.0

Notice that .by lists groups in the order they first appear in the data (E first, because the file starts with population AB from Tennessee), while group_by() uses the factor levels. Another small reason to set the factor order on purpose.

Many columns at once with across()

Summarizing five traits one at a time means typing mean(..., na.rm = TRUE) five times. across() applies one function, or several, to a whole set of columns:

fitness_traits <- c("SeedWeight", "Germination", "Survival", "Height", "Fitness")

traits |>
  group_by(Region) |>
  summarise(across(all_of(fitness_traits), \(x) mean(x, na.rm = TRUE)),
            .groups = "drop")
# A tibble: 3 × 6
  Region SeedWeight Germination Survival Height Fitness
  <fct>       <dbl>       <dbl>    <dbl>  <dbl>   <dbl>
1 C         0.00325       0.566    0.819   29.7    14.6
2 M         0.00305       0.647    0.820   34.0    19.8
3 E         0.00338       0.391    0.897   28.9    10.5
NoteCode breakdown: \(x) mean(x, na.rm = TRUE)

\(x) is shorthand for function(x). It creates a small, unnamed (anonymous) function in place. The line above is identical to:

summarise(across(all_of(fitness_traits), function(x) mean(x, na.rm = TRUE)))

across() calls that function once for each selected column and passes the column in as x. all_of(fitness_traits) says “use the columns named in this character vector, and error if any is missing”. That is safer than any_of(), which skips missing names without telling you.

To get several statistics per column, pass a named list of functions. The names become suffixes on the new columns:

traits |>
  group_by(Region) |>
  summarise(across(c(Height, Fitness),
                   list(mean = \(x) mean(x, na.rm = TRUE),
                        sd   = \(x) sd(x, na.rm = TRUE))),
            .groups = "drop")

New categories with case_when()

Elevation is continuous, but sometimes you want bands. case_when() is a vectorized if/else: conditions are checked in order, and the first one that is TRUE wins:

traits <- traits |>
  mutate(elev_class = case_when(
           Elevation < 500  ~ "low",
           Elevation < 1000 ~ "mid",      # only reached if Elevation >= 500
           Elevation >= 1000 ~ "high"
         ),
         elev_class = factor(elev_class, levels = c("low", "mid", "high")))

traits |> count(elev_class)
# A tibble: 4 × 2

NoteLogic check: where did the NA class come from?

count() shows 3 trees with elev_class of NA. In Module 1, colSums(is.na(traits)) reported 3 missing Elevation values. These are the same 3 trees, all from population NBTIC. No condition can be TRUE for a missing elevation, so case_when() returns NA for them.

That is the right behavior. A tree with unknown elevation should not be put in an elevation band. But count() lists the NA group openly, while table() from Module 1 hides it. That is one more reason to like count() for checking data.

Functions and iteration

Writing your own function

You wrote a small function (stats_of()) in Module 1, Exercise 3. Here is a more general version. It takes a data frame and the name of a trait as text, and returns a one-row tibble:

trait_summary <- function(data, trait) {
  x <- data[[trait]]                      # [[ ]] pulls a column by its name as text
  stopifnot(is.numeric(x))                # stop early with a clear error if not numeric

  tibble(trait     = trait,
         n         = sum(!is.na(x)),
         n_missing = sum(is.na(x)),
         mean      = mean(x, na.rm = TRUE),
         sd        = sd(x, na.rm = TRUE),
         cv        = sd / mean)           # coefficient of variation
}

trait_summary(traits, "Height")
# A tibble: 1 × 6
  trait      n n_missing  mean    sd    cv
  <chr>  <int>     <int> <dbl> <dbl> <dbl>
1 Height   313        13  30.0  4.64 0.155
NoteLogic check: why data[[trait]] and not data$trait?

data$trait looks for a column literally called trait, and there isn’t one. data[[trait]] evaluates the variable trait first (giving "Height"), then pulls that column. Use [[ ]] whenever the column name is stored in a variable. That is almost always the case inside functions and loops.

stopifnot() is a cheap guard. Calling trait_summary(traits, "Region") stops at once with is.numeric(x) is not TRUE, instead of returning a confusing NA mean with a warning. Functions that fail early and loudly are much easier to debug than ones that fail quietly later on.

Inside tibble(), cv = sd / mean uses the sd and mean columns defined just above it in the same call, like mutate() does. It does not refer to the functions sd() and mean().

TipWhich one should I use?

Both are fine. A for loop is easier to read when each step does several things (read a file, fit a model, save a plot). map() is shorter when each step is a single function call that returns a value. Choose the one you can still read six months from now.

One habit to drop: growing a result inside a loop with out <- rbind(out, new_row). R copies the whole object on every pass, so it gets slow quickly with large data (for example, thousands of SNPs). Make room first, as above, or use map().

How to read the region coefficients: Region is a factor, so lm() makes the first level the reference. Thanks to fct_relevel() that is C (Core). RegionM ≈ +4.56 means Margin trees average about 4.6 fitness units above Core trees at the same elevation. RegionE ≈ −2.15 is the Edge-vs-Core difference, and its p ≈ 0.07 is not clearly separable from zero once elevation is in the model.

The anova() comparison (F = 9.2, p ≈ 1.3 × 10⁻⁴) says Region adds real explanatory power beyond elevation.

The general lesson: when a predictor (elevation) is correlated with group structure (region), a model without the groups gives the predictor credit for the group differences. Here “region” partly stands for genetic background. This is the same problem genotype–environment association methods face with population structure, and it is why the population genetics module corrects for structure (with PCs like the PC1 and PC2 columns) before testing environmental associations.

Wrap up

Idea check

Answer these in your own words, as comments at the top of src/02_wrangle_model_traits.R.

  1. What does x |> f(y) translate to, and why do dplyr verbs chain together so naturally?
  2. When would you use group_by() |> summarise() instead of group_by() |> mutate()? (Hint: how many rows does each return?)
  3. Give one task that is easier with long data and one that is easier with wide data.
  4. After a left_join(), your table has more rows than before. What happened, and how do you find the cause?
  5. In ggplot(), what is the difference between aes(colour = Region) and colour = "blue"?
  6. Why did the elevation slope shrink when Region was added to the model? What does this have to do with population structure?
TipSample answers
  1. f(x, y): the left side becomes the first argument. Every dplyr verb takes a data frame first and returns a data frame, so each verb’s output can be the next one’s input.
  2. summarise() collapses each group to one row (a summary table). mutate() keeps every row and adds a column computed within each group. An example is group_by(Population) |> mutate(fitness_rel = Fitness / mean(Fitness, na.rm = TRUE)), which gives each tree’s fitness relative to its own population’s mean.
  3. Long is easier for doing one operation across many variables, like faceted plots or group_by(trait) summaries. Wide is easier for comparing variables side by side: correlations between traits, model formulas like Fitness ~ Elevation, and readable summary tables.
  4. The key is not unique in the right-hand table, so some rows matched more than once and were copied. Find the culprits with count(y, key) |> filter(n > 1).
  5. Inside aes() you map a column to colour, so colour changes with the data and a legend appears. Outside aes() you set a fixed colour for the whole layer.
  6. Elevation and region are confounded: Edge populations are high and southern, Margin populations are low. Without Region, the model credits elevation with differences that are really between regions. Region here partly stands for genetic background, which is exactly why genotype–environment analyses must account for population structure before testing environmental effects.
